# طرح سیستم آپدیت و مجوز (برای همه‌ی محصولات A-Delnaz)

این سند همه‌ی تصمیم‌های گرفته‌شده را نگه می‌دارد. هر چت جدیدی که روی آپدیت یا مجوز کار می‌کند، اول این را بخواند.
وضعیت هر بخش در جدول آخر سند است.

---

## بخش ۱: تصمیم‌ها (به زبان ساده)

### ۱-۱. آپدیت

1. هر محصول یک مخزن انتشار **عمومی** دارد، به نام `<Product>-Releases` (مثل `Domainator-Releases`، `Security-Reports-Releases`).
   کد محصول در مخزن خصوصی خودش می‌ماند.
2. **همه‌ی نسخه‌ها نگه داشته می‌شوند** (هم در گیت‌هاب، هم در پوشه‌ی اشتراکی). گیت‌هاب برای حجم کل و پهنای باند فایل‌های انتشار محدودیتی ندارد؛ فقط هر فایل باید زیر ۲ گیگابایت باشد.
3. برای هر نسخه سه نوع فایل:
   - **فایل آپدیت سایت** با پسوند `.adup`: رمزنگاری‌شده و امضاشده. ویندوز آن را باز نمی‌کند و با Notepad فقط حروف درهم دیده می‌شود. برای کشیدن در کادر سایت یا گرفتن از منبع.
   - **آپدیت ویندوزی** (`...-Update-x.y.z.exe`): برای اجرا روی خود سرور.
   - **نصب‌کننده‌ی کامل** (`...-Setup-x.y.z.exe`): برای نصب جدید.
   - فایل‌های `exe` کد برنامه را بدون رمز دارند (با ابزار رایگان باز می‌شوند)، پس **هرگز در مخزن عمومی نمی‌روند**:
     فقط در انتشار (Release) خصوصی مخزن کد محصول. بعدها از پنل کاربری سایت به مشتری داده می‌شوند.
4. فایل‌ها **در خود گیت‌هاب** ساخته می‌شوند (GitHub Actions)، نه روی کامپیوتر کاربر. اینترنت کاربر مصرف نمی‌شود.
   ساختن روی کامپیوتر خود کاربر با `dev.cmd` هم می‌ماند؛ در آن حالت فایل‌ها مستقیم در پوشه‌ی اشتراکی هم می‌روند.
5. **صفحه‌ی آپدیت سایت‌ها تغییر ظاهری نمی‌کند.** همان چهار راه می‌ماند: گیت‌هاب، آدرس اینترنتی، پوشه‌ی اشتراکی (فقط مسیر پوشه)، بارگذاری دستی.
   فقط پشت صحنه عوض می‌شود: فرمت `.adup`، بررسی امضا، بررسی مجوز. فایل `update.json` دیگر لازم نیست.
6. **برنامه‌ی واسط (Mirror):** روی یک کامپیوتر ویندوزی همیشه‌روشن شرکت که هم اینترنت دارد و هم به پوشه‌ی اشتراکی دسترسی دارد.
   هر چند وقت یک بار مخزن‌های انتشار همه‌ی محصولات را بررسی می‌کند و فایل‌های جدید را در `<پوشه‌ی اشتراکی>\<Product>\` می‌گذارد.
   یک بار نصب می‌شود؛ برای هر پروژه کاری لازم ندارد. به مشتری‌ها هم می‌شود داد (اختیاری).
7. در هر محصول، **منبع آپدیت قابل تغییر است** (گیت‌هاب امروز، سایت خود کاربر در آینده). چون فایل‌ها امضا دارند، منبع مهم نیست.

### ۱-۲. مجوز

1. **کد نصب (سریال نصب):** هر نصب جدید یک کد تصادفی می‌سازد و در دیتابیس خود برنامه نگه می‌دارد.
   با جابه‌جایی ماشین مجازی بین هاست‌ها عوض نمی‌شود (چون در دیتابیس است). هیچ مشخصه‌ی سخت‌افزاری یا دامنه‌ای قفل نمی‌شود.
2. **فایل مجوز** (`.adlic`): رمزنگاری‌شده با کلیدی که از **کد نصب همان شرکت** ساخته می‌شود و امضاشده با کلید مجوز.
   - با Notepad خوانا نیست.
   - روی نصب دیگری باز نمی‌شود.
   - دستکاری‌اش امضا را خراب می‌کند.
3. **داخل مجوز:**
   | بخش | توضیح |
   |---|---|
   | شناسه‌ی مجوز | یکتا |
   | محصول | هر مجوز برای یک محصول |
   | خریدار | نام شرکت، با چند شکل مجاز (فارسی و انگلیسی) |
   | کد نصب | نصبی که مجوز برایش ساخته شده |
   | نوع | `full` یا `trial` |
   | بخش‌ها (ماژول‌ها) | همه، یا فهرست؛ هر بخش می‌تواند تاریخ پایان جدا داشته باشد |
   | مدت استفاده | بی‌نهایت یا تا تاریخ |
   | مدت آپدیت | آپدیت‌هایی که بعد از این تاریخ **منتشر** شده‌اند نصب نمی‌شوند |
   | مدت پشتیبانی | جدا از آپدیت |
   | سقف فعال‌سازی | برای شمارش در ابزار مجوز و بعدها سایت |
   | محدودیت‌ها (اختیاری) | تعداد کاربر و مانند آن |
4. **پایان مدت استفاده:** هشدار از یک ماه قبل → چند روز فرصت → **فقط‌خواندنی** (اطلاعات دیده و خروجی گرفته می‌شود، ثبت جدید نه).
5. **پایان مدت آپدیت:** برنامه کار می‌کند؛ فقط نسخه‌هایی که بعد از آن تاریخ منتشر شده‌اند نصب نمی‌شوند (تاریخ انتشار داخل فایل `.adup` امضا شده است، پس عوض کردن ساعت سرور اثری ندارد). همین برای نصب‌کننده‌ی کامل هم برقرار است.
6. **مجوز آزمایشی:** همان مجوز با نوع `trial` و تاریخ پایانی که کاربر (فروشنده) دستی تعیین می‌کند (یک هفته، یک ماه...). روی صفحه‌ها و گزارش‌ها «نسخه‌ی آزمایشی» نوشته می‌شود. اگر همان شرکت خرید، مجوز اصلی روی همان نصب می‌نشیند و اطلاعات حفظ می‌شود.
7. **مجوز در نصب‌کننده:** نصب بدون مجوز ادامه پیدا نمی‌کند. نصب‌کننده کد نصب را نشان می‌دهد (با QR). راه‌ها: فعال‌سازی آنلاین (بعد از راه‌افتادن سایت)، فایل مجوز، یا مجوز آزمایشی.
8. **صفحه‌ی مجوز در تنظیمات هر محصول:** خریدار، بخش‌های فعال، تاریخ‌ها؛ آنلاین: درخواست تمدید؛ آفلاین: بارگذاری فایل جدید.
9. **نام خریدار و نام نمایشی:**
   - نام نمایشی شرکت در تنظیمات آزاد است (مثل الان).
   - اگر با نام‌های مجاز خریدار در مجوز یکی نبود، **یک بار** پرسیده می‌شود: «این مجوز به نام شرکت X خریداری شده؛ مطمئنید در شرکت درستی نصب می‌کنید؟». تأیید (چه کسی، کی) ثبت می‌شود.
   - بعد از آن تأیید، همه‌ی گزارش‌ها **Watermark** نام خریدار واقعی را دارند.
   - برای جلوگیری از هشدار بی‌جا، مجوز چند شکل از نام را می‌پذیرد (مثلاً «پرستیژلند» و «Prestige Land»).
   - **Watermark پنهان** همیشه هست: شناسه‌ی مجوز در مشخصات داخلی خروجی‌ها (PDF، اکسل) نوشته می‌شود تا اگر نسخه‌ی غیرقانونی پیدا شد، معلوم شود از کدام مجوز نشت کرده.
   - زیرنویس «دارای مجوز برای ...» در صفحه‌ها **نمی‌گذاریم** (تصمیم کاربر).
10. **سقف فعال‌سازی و انتقال:** هر مجوز سقف نصب دارد (مثلاً ۲). انتقال به سرور دیگر محدود است (مثلاً هر ۶ ماه یک بار). شمارش فعلاً در ابزار `License-Manager` (داده‌ها در مخزن خصوصی `License-Data`) و بعدها در سایت.
11. **تشخیص آنلاین (بعد از راه‌افتادن سایت):** نصب‌های آنلاین هر چند وقت یک بار خبر می‌دهند. یک کد نصب از دو جا → پرچم.
12. **محدودیت صادقانه:** کپی کامل یک نصب فعال روی سرور کاملاً آفلاین قابل جلوگیری نیست؛ با Watermark و قرارداد پوشش داده می‌شود.

### ۱-۳. کلیدها

| کلید | کار | کجا نگه داشته می‌شود |
|---|---|---|
| کلید امضای آپدیت (Ed25519) | امضای فایل‌های `.adup` | Secrets گیت‌هاب + فلش کاربر (رمزنگاری‌شده با رمز کاربر) |
| کلید امضای مجوز (Ed25519) | امضای فایل‌های `.adlic` | **فقط** فلش کاربر، رمزنگاری‌شده. هرگز روی اینترنت. |
| کلید محتوای هر محصول (AES-256) | رمزنگاری محتوای `.adup` | داخل کد محصول + Secrets گیت‌هاب |
| کلید عمومی‌ها | بررسی امضا | داخل کد هر محصول |

- از فایل کلیدهای رمزنگاری‌شده حتماً نسخه‌ی پشتیبان جدا نگه داشته شود. رمز فراموش‌شده قابل بازیابی نیست.
- اگر کلید امضای آپدیت لو برود، کلید مجوز امن می‌ماند و برعکس.

### ۱-۴. ابزار ساخت مجوز (`License-Manager`)

- برنامه‌ی ویندوزی **قابل حمل** (یک فایل `exe`، دات‌نت، رابط فارسی)، روی فلش.
- داده‌ها (مشتری‌ها، مجوزها، فعال‌سازی‌ها) در مخزن **خصوصی** `License-Data`، با نسخه‌ی محلی:
  - آنلاین: هر تغییر فوراً فرستاده می‌شود.
  - آفلاین: کار عادی ادامه دارد؛ تغییرها در صف می‌مانند و بعد از وصل شدن خودکار فرستاده می‌شوند.
  - هر مجوز یک فایل جدا با شناسه‌ی یکتا (بدون تداخل بین دو کامپیوتر).
  - کتابخانه‌ی گیت داخل خود ابزار است (نصب گیت لازم نیست).
- کلید دسترسی گیت‌هاب (Token) فقط به همان یک مخزن، رمزنگاری‌شده روی فلش.
- امکانات: ساخت/تمدید مجوز، مجوز آزمایشی با مدت دلخواه، شمارش فعال‌سازی، فهرست مجوزهای رو به پایان، ارسال با ایمیل.
- Claude به `License-Data` دسترسی نمی‌گیرد (اطلاعات مشتری‌ها در چت‌ها نمی‌آید).
- بعدها همین منطق به پنل کاربری سایت منتقل می‌شود؛ فرمت فایل مجوز عوض نمی‌شود.

## بخش ۲: مشخصات فنی

### ۲-۱. فرمت فایل آپدیت `.adup` (نسخه‌ی فرمت 1)

```
"ADUP" (4 بایت) | 0x01 (نسخه‌ی فرمت) | IV (16 بایت) | ciphertext
ciphertext = AES-256-CBC + PKCS7 (کلید محتوای محصول) از:
    header_len (uint32, little-endian) | header (JSON, UTF-8) | signature (64 بایت) | payload (zip)
signature = Ed25519(کلید امضای آپدیت) روی:  "ADUP1" + header
```

- همه‌چیز (حتی header) رمز شده است؛ هیچ بخشی خوانا نیست.
- CBC انتخاب شد چون هم پایتون و هم دات‌نت آن را به‌صورت جریانی (Stream) دارند (فایل بزرگ لازم نیست کامل در حافظه باشد).
- رمزنگاری فقط برای پنهان کردن است؛ اعتبار با امضا و SHA-256 داخل header بررسی می‌شود.
- **header:**
  ```json
  {
    "format": 1,
    "product": "security-reports",
    "product_name": "Security Reports",
    "version": "1.0.9",
    "released_at": "2026-11-18T12:00:00Z",
    "payload_size": 12345678,
    "payload_sha256": "…",
    "requirements_sha256": "…",
    "releases": [ { "version": "1.0.9", "date": "1405/08/27", "notes": ["…"] } ]
  }
  ```
- `payload` همان zip فعلی هر محصول است (برای Security-Reports: `app/…` و `version.txt`). پس اسکریپت نصب سرور (`apply-update.ps1`) عوض نمی‌شود: سایت فایل را بررسی و باز می‌کند و zip را در پوشه‌ی محافظت‌شده‌ی `updates` می‌گذارد.
- ابزار ساخت و بررسی: `release/adup.py` در همین مخزن (`keygen`، `pack`، `inspect`، `unpack`).

### ۲-۲. فهرست نسخه‌ها برای منبع «آدرس اینترنتی»

یک وب‌سایت را نمی‌شود مثل پوشه فهرست کرد. پس کنار فایل‌ها یک `index.json` (خودکار ساخته می‌شود) هست:
```json
{ "product": "security-reports", "versions": [ { "version": "1.0.9", "file": "Security-Reports-1.0.9.adup", "size": 123, "released_at": "…" } ] }
```
لازم نیست امضا داشته باشد، چون هر فایل `.adup` خودش را بررسی می‌کند.
- گیت‌هاب: آخرین انتشار از API گیت‌هاب.
- پوشه‌ی اشتراکی: سایت خودش فایل‌های `.adup` پوشه را می‌خواند و بالاترین نسخه‌ی معتبر را انتخاب می‌کند.

### ۲-۳. فرمت فایل مجوز `.adlic` (نسخه‌ی فرمت 1)

```
"ADLC" | 0x01 | IV (16) | ciphertext
key = HKDF-SHA256(ikm = رمز مجوز محصول، salt = کد نصب، info = "adlic-v1")
ciphertext = AES-256-CBC + PKCS7 از:  body_len (uint32) | body (JSON) | signature (64)
signature = Ed25519(کلید امضای مجوز) روی: "ADLC1" + body
```
- **کد نصب:** ۱۲۸ بیت تصادفی، به شکل `XXXXX-XXXXX-XXXXX-XXXXX-XXXXX` (Base32 بدون حروف گیج‌کننده + رقم کنترل).
- **body:**
  ```json
  {
    "format": 1, "license_id": "…", "product": "domainator",
    "licensee": { "name": "…", "aliases": ["…"] },
    "install_code": "…", "type": "full",
    "modules": { "*": null }  یا  { "ca": null, "dns": "2027-03-21" },
    "use_until": null, "updates_until": "2027-11-18", "support_until": "2027-11-18",
    "max_activations": 2, "limits": {}, "issued_at": "…"
  }
  ```

### ۲-۴. ساختن در گیت‌هاب (GitHub Actions)

- محرک: برچسب `v*` در مخزن محصول (با `dev.cmd` گزینه‌ی 9، یا Claude به درخواست کاربر).
- روی ویندوز گیت‌هاب: ساخت zip، ساخت `.adup`، ساخت `exe`ها (Inno Setup)، ساخت `index.json`، انتشار در `<Product>-Releases`.
- Secrets لازم در مخزن محصول: `ADUP_SIGNING_KEY`، `ADUP_CONTENT_KEY`، `RELEASES_TOKEN` (Token با دسترسی نوشتن فقط به مخزن‌های `*-Releases`).

### ۲-۵. نسخه‌ی پل (انتقال سرورهای فعلی)

سرورهایی که الان نصب هستند فقط zip و `update.json` را می‌شناسند. پس **اولین نسخه با سیستم جدید** یک بار به هر دو شکل منتشر می‌شود:
zip قدیمی + `update.json` (برای اینکه سرورهای قدیمی به آن برسند) و `.adup`. از نسخه‌ی بعد فقط `.adup`.
